Learn API Docs & Changelogs with Phoebe · Session 1 of 6

Docs are the API's first interface

A developer meets your documentation before they meet your endpoint, and most of them decide whether to keep going inside the first few minutes. So the docs are not a description of the API: for the person reading them, they are the API. Tonight we name the five jobs readers bring to API docs, make time to first call the number we argue about, and run a five-minute audit on the docs of Parcelpoint, a constructed parcel-locker API whose v1 docs grew the way most docs grow, one page at a time.

Part 0

Where we start

Two questions run through all six sessions. Could a stranger make a first successful call in five minutes? And when version 2 lands, would they know from your changelog exactly what to do? Everything else, from the OpenAPI spec to the deprecation header, is in service of those two. We carry one running case the whole way: the Constructed Parcelpoint example, a public REST API for parcel lockers, with lockers, parcels, reservations and webhooks for pickup events. Part 1 · covers the reader's jobs and the four doc kinds

Five readers, five different pages

6 min live

"The docs" are not one thing with one reader. The same developer arrives five times with five different questions, and a page that answers one of them well usually answers the others badly. The five jobs below are a working frame rather than a published standard: they are the questions people actually type into a docs search box, in the order a real integration asks them.

LiveThe five jobs, and what each one punishes4 min▶

Evaluate. A tech lead with three candidate APIs and an afternoon. They want what it does, what it does not, and what it costs to try. They punish marketing copy and a signup wall in front of the reference.

First call. The same person, ten minutes later, with a terminal open. They want a key, the base URL, the auth header and one request they can paste. They punish anything that sends them to a second page before the first 200.

Integrate. A week later, building the real feature. They want task recipes: how to page through lockers, how to retry safely, how to verify a webhook. They punish a reference page pretending to be a guide.

Debug. Production is returning 409 and nobody knows why. They want the exact meaning of every status code and field, fast, with the fix. They punish prose. This is the reference page's whole job, and session 3 is built around it.

Upgrade. Version 2 is announced. They want the list of what breaks for them, the date it stops working and the change to make. They punish a changelog that reads like a commit log. Sessions 5 and 6 are built around this reader.

Self-studyThe four doc kinds, applied to an API (one-card recap)3 min▶

The Diataxis framework sorts documentation into four kinds: tutorials, how-to guides, reference and explanation. The full map and its compass live in Learn Tech Writing, session 5, and that is where to learn it; here is only how it lands on an API.

The quickstart is the API's tutorial. Recipes for pagination, retries and webhooks are how-to guides. The endpoint pages are reference, and Diataxis's own advice for reference fits APIs exactly: describe the machinery, and mirror the structure of the product, which for an API means one page per resource or operation, in the order of the spec. "Why cursors and not page numbers" is explanation. The changelog does not sit neatly in any of the four; tech writing session 6 treats it as the project's memory, and session 6 here adds what is API-specific about it: versions, deprecation and sunset.

Real world

A reference page built for the debug reader. GitHub's REST reference entry for "Create an issue" lists, under one heading, the headers, the path parameters, the body parameters and every HTTP status code the call can return: 201, 400, 403, 404, 410, 422 and 503, each with its meaning, followed by a code sample. Nothing on it explains what an issue is or why you might want one. That is not an omission; that reader is somewhere else.

Part 2 · covers time to first call

Time to first call is the number

5 min live

Time to first call is the elapsed time from a developer first landing on your docs to their first successful response. It is a docs metric disguised as an API metric: the endpoint answers in milliseconds, so almost every minute of it is spent reading, hunting and fixing. Below is one reader's audit of the Parcelpoint v1 docs, stopwatch running.

LiveWhy this number and not page views or satisfaction3 min▶

Page views reward docs people get lost in. Satisfaction surveys reach the people who stayed. Time to first call measures the one moment every integration passes through, and it moves when the docs change: put the base URL and the auth header on the first screen and the 3:10 in the figure becomes 0:50 without touching a line of the API.

It has two honest limits. Measured from analytics, it only sees the people who succeeded; the reader who gave up at 4:50 never records a time at all, so track how many people start the quickstart and never finish it alongside the median time. And it says nothing about the four readers who come after. A fast quickstart in front of a reference that lies is a fast way to a slow week.

The five-minute bar used in the audit tonight is a working target, not an industry constant. Pick your own bar, write it down, and measure against it the same way every time, exactly like any other metric.

Self-studyThe vendor number, read as a vendor number2 min▶

The phrase "time to first call" is pushed hardest by Postman, whose blog post "Improve your time to first API call by 20x" (2023) opens with the claim that it is the most important API metric. The post reports one publisher's first call taking about 17 minutes, about 10 with a ready-made Postman collection, and a range of 1.7 to 56 times faster across publishers who used a forked collection.

Read that the way you read any vendor study of its own product: the direction is plausible, the size is not independently checked, and the method (which developers, which tasks, who timed it) is not published in enough detail to repeat. The idea survives without the number. Measure your own API, before and after one change, and quote that.

Real world

The claim and its source in one sentence. When a vendor says its tool makes first calls "up to 56 times faster", the honest restatement is: a tools company measured developers using its own tool and reports a range whose top end is 56. That sentence is not cynical. It is the sentence you would want written about your own launch numbers.

Part 3 · covers the docs kit and why it starts from a spec

The docs kit, and the one file that feeds it

4 min live

Parcelpoint's v1 docs grew by accretion: a page per feature, written when the feature shipped, by whoever shipped it. Nothing connects them, so nothing keeps them true. Over six sessions we replace the pile with a kit in which one machine-readable description of the API feeds the reference, the examples and the changelog, so a change made once shows up everywhere it should.

LiveWhy the docs are the interface, and the code is the implementation3 min▶

A developer writing against Parcelpoint never sees its code. They see a page saying POST /parcels takes locker_id, recipient_phone and a size of small, medium, large or xl, and they write their client against that page. From that moment the page is a promise, and a server that disagrees with it is the bug, whichever one was written first.

That is why the kit puts a machine-readable spec in the middle. If the reference page is written by hand next to the code, the two drift apart in silence; if the reference, the examples and the changelog are generated from or tested against the same file the server is checked against, a drift turns into a failing build instead of a confused customer. Session 2 writes that file. Session 4 makes drift fail a test. Session 5 makes a breaking change impossible to ship without noticing.

Self-studyWhat a docs kit is not2 min▶

It is not a portal product. Hosted docs platforms, API clients with shareable collections and design studios all exist and many teams use them; they are a choice about where the kit is published, named here as a category, and every build-along in these six sessions runs in the page with no account. It is also not the docs-as-code pipeline itself (version control, review, preview builds), which Learn Tech Writing, session 7 owns. The kit is what goes through that pipeline.

Real world

A changelog built for the upgrade reader. Stripe's API changelog gives every change its own row, and every row carries an explicit "Breaking change?" column that reads Breaking or Non-breaking. Breaking changes are not tucked into a separate section; they sit in the same table, marked, so the reader scanning for "does this affect me" reads one column. Session 6 comes back to how Stripe pairs that column with dated API versions.

Build-along

The five-minute audit of Parcelpoint v1

★ 22 min · everyone builds

Below is the Parcelpoint v1 developer docs landing page, exactly as it grew (Constructed Parcelpoint example). You will read it as a first-call reader with a timer running, check its example against the API's own contract, and score it. Nothing to install: the page and the scorecard are the whole kit for tonight.

Start a five-minute timer and read the landing page as a stranger. You are a developer at a shop that wants to drop parcels into Parcelpoint lockers. Your only goal is one successful POST /parcels. Note the time at each moment you find something you needed.

★ Step 1 · the Parcelpoint v1 landing page, as it grew (constructed)PARCELPOINT DEVELOPER DOCS 1. Overview Parcelpoint is a network of smart parcel lockers. Our REST API lets partners find lockers, register parcels and reserve slots. 2. What's new 1.2.0 Added size class xl. 1.3.0 Added open_24h to lockers. 1.4.2 Fixed created_at timezone on parcels. 3. Webhooks POST /webhooks with a url and the events you want: parcel.delivered, parcel.picked_up, parcel.expired. 4. Create a parcel curl -X POST https://api.parcelpoint.example/parcels \ -d '{"locker": "LK-0042", "phone": "+1 555 0100", "size": "M"}' 5. FAQ How do I authenticate? Send your key in the X-Api-Key header. Where do I get a key? Ask your account manager.

Check the example against the contract. This is what Parcelpoint's own OpenAPI document says POST /parcels requires (the same document the session 5 bench loads). Put the example from step 1 next to it and list every way the example would fail.

★ Step 2 · what the API actually requires (v1.4.2)servers: https://api.parcelpoint.example/v1 security: apiKey, sent as the X-Api-Key header POST /parcels requestBody (required, application/json): ParcelCreate locker_id string required recipient_phone string required size string required one of: small, medium, large, xl responses: 201 Parcel created 400 The request body is invalid 409 The locker has no free slot of that size

Write the defect list. Each defect gets one line: what is wrong, where the reader hits it, and the fix. There are at least six; compare yours with the list below only after you have written your own.

★ Step 3 · one reading of the defects1. Base URL in the example lacks /v1 -> 404 before anything else 2. No X-Api-Key header in the example -> 401; the fix is in the FAQ 3. No Content-Type: application/json header -> body may not parse 4. "locker" and "phone" are not the field names -> 400; the spec says locker_id and recipient_phone 5. size "M" is not in the enum -> 400; the spec says medium 6. "Ask your account manager" for a key -> the first call cannot happen today at all for a self-serve reader 7. What's new runs oldest first -> the upgrade reader scrolls

Rewrite the first screen. Use the "after" order from the figure: base URL and auth, one request that works, the response, the two likely errors, then links onward. Keep it under twenty lines. The request must match step 2 exactly.

★ Step 4 · a first screen that passesBase URL https://api.parcelpoint.example/v1 Auth X-Api-Key: <your key> (keys: Dashboard > Developers) curl -X POST https://api.parcelpoint.example/v1/parcels \ -H "X-Api-Key: $PARCELPOINT_KEY" \ -H "Content-Type: application/json" \ -d '{"locker_id": "LK-0042", "recipient_phone": "+1 555 0100", "size": "medium"}' You should get 201 Created and a parcel with a pickup_code. 401 your key is missing or wrong: check the X-Api-Key header 409 that locker has no free medium slot: try GET /lockers?city=... Next: the POST /parcels reference, then "Receive pickup webhooks".

Score both versions. Grade the original landing page on the scorecard below, honestly, then grade your rewrite. Write both totals at the top of your audit file. That file is piece one of Parcelpoint's docs kit, and session 6 scores the whole kit with the same honesty.

The base URL, with its version, is on the first screen Not only inside an example, and not on a separate "environments" page.
How to get a key, and where it goes, comes before the first example Self-serve if at all possible. "Ask your account manager" scores 0 for a first-call reader.
One request can be pasted as-is and succeeds Every field name and enum value checked against the spec, every header present.
The expected response is shown The status code and the one field the reader needs next (here, pickup_code).
The likely first errors are named with their fix For a first call that is usually 401 and one domain error, such as 409 here.
The page ends by sending the reader onward To the reference for the call they just made, and to the guide for the next task.

Time it on someone else. Your own docs are unreadable to you; you already know where everything is. The cheapest honest time-to-first-call measurement is a colleague from another team, a screen share, and you saying nothing for five minutes.

Homework

Before session 2

30 min
  1. Run the five-minute audit on an API you depend on (a payment provider, a maps API, an internal service). Note the time at each moment you found something you needed, and where you found it.
  2. Run it on your own API's docs, on a colleague. Say nothing. Write down the first three places they hesitated.
  3. Sort your docs pages by reader job. One column per job from Part 1. Pages that serve two jobs badly go in both columns with a question mark; those are the pages to split.
  4. Find the contract. Does your API have a machine-readable description today (an OpenAPI file, a generated one, a schema anywhere)? Bring the answer to session 2, where we write Parcelpoint's.
Check yourself

Three questions

Clear all three and session 1 gets stamped in your passport.

1 · A reader in production is getting a 409 from POST /parcels and wants to know why. Which page should answer them, and what does it owe them?

That is the debug job, and the reference is the debug reader's page. A quickstart that tried to list every error would fail its own reader, and the overview is for someone still deciding whether to use the API at all.

2 · In the audit, the first 201 arrives at 7:20 and the API itself answered in under a second. What does that tell you?

The hatched stretches are minutes with addresses: a line in the wrong place, a key behind an email, a field name that drifted. The five-minute bar is a working target to measure against, not a published constant.

3 · Why does Parcelpoint's docs kit put an OpenAPI spec in the middle, feeding the reference, the examples and the changelog?

The docs are the promise developers code against. A single machine-readable source is what lets the promise and the server be checked against each other. The quickstart still matters; session 4 tests it against the same spec.
