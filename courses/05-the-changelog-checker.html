Part 1 · covers what counts as breaking

The rule table, and the asymmetry under it

6 min live

"Breaking" sounds like a judgement call. It is mostly a mechanical one, with a short list of genuine disagreements. A change breaks a caller when a request that used to succeed now fails, or when something the caller reads is no longer there. Everything in the engine's 28 rules is one of those two tests, applied to a particular part of the description.

LiveRequests may only widen; responses may only grow4 min▶

The two questions produce an asymmetry worth memorising. On the request side, the API is the one checking: it may accept more than before (a new optional field, an extra enum value, a required field made optional) but never less, because every narrowing turns some caller's working request into a 400. On the response side, the caller is the one reading: the API may send more than before (a new field, a new status code for a new situation) but never less, because a caller somewhere reads the field you removed.

That is why the same edit lands differently on each side. In the Petstore preset, removing pending from the pet status list is breaking on POST /pet and PUT /pet, where callers send it, and non-breaking on the five operations that only return pets, where a caller simply never sees the value again. One schema change, two verdicts, decided by direction.

Self-studyWhere the published rule lists disagree, and which side the engine takes4 min▶

The rule table is built from two published sources read for this session: the breaking-changes list of oasdiff, an open-source OpenAPI diff tool, and GitHub's REST "API versions" page, which lists what GitHub treats as breaking and as additive. They agree on most rows. They disagree on three, and the disagreement is the lesson.

Removing an optional response field. GitHub lists "removing or renaming a parameter or response field" as breaking. oasdiff classifies a removed required response property as breaking but a removed optional one as informational, on the reasoning that a client already had to cope with its absence. The engine follows GitHub: a field that was documented and usually present is one somebody reads.

A new value in a response enum. GitHub lists adding enum values as additive. oasdiff raises it as a warning, because a client with an exhaustive switch over the values crashes on the new one. The engine follows GitHub and calls it non-breaking; the Recipient app in the consumer panel is the client oasdiff is worried about, and Part 3 comes back to it.

Removing a parameter. GitHub: breaking. oasdiff: "potentially breaking" (a warning), since many servers ignore unknown parameters and the old call still succeeds. The engine follows GitHub, because a caller still sending page to a cursor API gets the first page forever and no error to tell them.

None of these is settled. Write your own team's choice down next to your rule table, and say which source it follows.

Self-studyWhat the engine compares, and what it cannot see2 min▶

It compares paths and operations, parameters (path-level ones merged in), request bodies and responses for the JSON media type, and auth requirements, following $ref pointers into components. It reads OpenAPI 3.0 nullable: true and the 3.1 type array ["string", "null"] as the same thing, so a migration between them is not reported as a type change.

It does not compare top-level webhooks, callbacks, links, response headers, non-JSON media types, or a response field changing from required to optional; it reads JSON only, because no YAML parser is loaded in the page. And it cannot see intent. A rename arrives as one removal and one addition, which is the truth for the caller: the old name stops working. A bug fix is invisible, because the description did not change, which is why the drafted entry never has a Fixed or Security section.

Build-along · the bench

Four diffs, computed in front of you

★ 26 min · the main event

Run the four presets in the order below. For each one, read the bump first, then the three counts, then the change table from the top (breaking rows sort first), then the drafted entry. Say out loud which lines you would rewrite before publishing. After the fourth, open the editor and make one change of your own.

Parcelpoint v1 to v2. The bench prints MAJOR, 1.4.2 to 2.0.0, from 30 changes: 12 breaking, 16 non-breaking, 2 docs only. Read the twelve breaking rows. Find the rename: locker_id removed and id added, twice each, once per operation that returns a locker. Find the pagination change as four rows, two parameters removed and two added, plus the response fields that went with them.

Parcelpoint v1 to v1.5. MINOR, 1.4.2 to 1.5.0, from 7 changes: 0 breaking, 6 non-breaking, 1 docs only. This is the release that should have come first: it adds free_slots to the locker, adds an optional recipient_email, and marks the status endpoint deprecated. SemVer rule 7 is why deprecation alone forces a minor.

Parcelpoint wording fix. PATCH, 1.4.2 to 1.4.3, from 3 changes, all docs only. Three descriptions edited and nothing a client can detect. Check the drafted entry: every line is marked "(docs only)", which is your cue to decide whether it belongs in the public changelog at all.

Swagger Petstore, edited. MAJOR, from 14 changes: 3 breaking, 10 non-breaking, 1 docs only. The old document is the real Petstore sample (OpenAPI 3.0.4, Apache-2.0); the new one has six edits. Find the one schema edit that produced seven rows: pending leaving the pet status list. The version goes 1.0.30-SNAPSHOT to 2.0.0, because the engine drops the pre-release label before bumping.

Make one change of your own. Load Parcelpoint v1 to v1.5, open "Edit the two documents", find "recipient_email" in the new document's ParcelCreate and add it to that schema's required list. Run the diff. The bench should now print MAJOR, with "new required request field recipient_email" as the breaking line. One word in a list moved the release from 1.5.0 to 2.0.0.

★ The edit, in the new document"ParcelCreate": { "type": "object", "required": ["locker_id", "recipient_phone", "size", "recipient_email"], ...

Read the draft, then rewrite it. The drafted entry is correct and machine-shaped: "request field size no longer accepts xl (POST /parcels; POST /reservations)". A human version says why and what to do: "Size class xl is retired; send large instead." Session 6 turns the draft into the entry a reader can act on. The diff makes sure nothing is missing; the writing makes it usable.

Part 2 · covers what the four diffs show

Four releases, four different shapes

5 min live

Put the four results side by side and the version number stops being a feeling. A release is a MAJOR the moment one line is breaking, however many friendly additions surround it, and the count of additions tells you nothing about how hard the upgrade will be.

LiveParcelpoint v2, read as a list of broken promises3 min▶

Grouped the way the drafted entry groups them, the twelve breaking changes become ten lines. Removed (7 lines): the status endpoint; the page and per_page parameters; the locker_id, page and total_pages response fields; the 201 response on reservations. Changed (3 lines): webhooks moved from the API key to a bearer token; recipient_email is a new required field; size xl is no longer accepted on parcels or reservations.

Each of the ten needs a sentence in session 6's migration guide: what to send or read instead, and by when. Notice that the bench found the 201-to-202 switch on POST /reservations, which no one would list as a "feature": a client that checks for 201 treats every reservation as a failure from the day v2 ships.

Self-studyWhy a long list of additions does not soften a major2 min▶

Semantic Versioning 2.0.0 sets the bump by the most serious change: MAJOR for incompatible API changes, MINOR for backward-compatible functionality, PATCH for backward-compatible bug fixes. It has no notion of averaging. Twelve breaking changes and sixteen additions is a major release with sixteen additions in it, and the additions can be shipped earlier, in a minor, if the team wants them out sooner. That is exactly what the v1.5 preset is: the additive half of v2, released on its own.

Part 3 · covers the anti-lever

Ship it as a minor, and count who breaks

6 min live

The bench has a second button: Ship it as a minor. It is the decision every team is tempted by when the major release feels too big to announce. Load Parcelpoint v1 to v2 and press it. The diff does not change; the version does, and so does what happens to the six constructed consumers of the API.

LiveWhy a wrong version number is worse than no version number3 min▶

Version numbers are read by machines before people. A client library that depends on "any 1.x at or above 1.4.2" (a caret range such as ^1.4.2 in npm works this way) treats 1.5.0 as safe to install automatically. Shipped honestly, 2.0.0 sits outside that range: nothing upgrades until a person decides to, and that person can read the migration guide first. Shipped as 1.5.0, the upgrade happens on the next deploy of every consumer, and the first anyone hears of the renamed field is an error in production.

On the bench, with v1 to v2 loaded: the honest bump prints 0 of 6 broken without warning, 4 of 6 warned and must migrate. Ship it as a minor and it prints 4 of 6 broken without warning, with the version reading 1.5.0. The four are the Shopfront checkout plugin (six hits, from page to the xl size), the Courier handheld app (the removed status endpoint and the lost 201), the Partner analytics export (total_pages) and the SMS notification service (the auth change).

Self-studyThe two consumers that did not break, and what the panel is3 min▶

The Locker kiosk firmware reads only address and open_24h from a locker, and cancels reservations; nothing it touches changed. The Recipient mobile app reads a parcel's status, which in v2 may now return returned. By the rule table that is non-breaking, and the panel counts it as unaffected. If the app's code handles the four old statuses in an exhaustive switch with no default, it will still fall over on the first returned parcel. That is precisely oasdiff's reason for warning on new response enum values, and it is the case for writing "status may return new values; handle unknown ones" in your reference from day one.

The consumer panel is a simulation. The six consumers and the fields each one reads are constructed for teaching; a consumer counts as broken when a breaking change is operation-wide (a removed operation, an auth change, a new required input, a lost success status) or names a field it reads. Real impact needs real usage data, such as which fields your clients actually send and read. The diff underneath is real.

Real world

Making breaking changes rare, on purpose. Since its 2024-09-30.acacia release, Stripe ships API versions monthly with no breaking changes, and twice a year issues a major release that starts with a version containing them. Each row of its changelog carries an explicit "Breaking change?" column. That is the policy version of tonight's bench: the classification is decided before the release is named, never after.

Check yourself

Three questions

Clear all three and session 5 gets stamped in your passport.

1 · In the Petstore preset, removing pending from the pet status list is reported as breaking on two operations and non-breaking on five. Why?

Requests may only widen; responses may only grow. A narrowed enum is a narrowing on the request side and a shrinking set of possible values on the response side, and only the first breaks a working caller.

2 · With Parcelpoint v1 to v2 loaded, what changes when you press "Ship it as a minor"?

The diff is a fact about the two documents and does not move. The version is a decision, and a minor tells every "any 1.x" client it is safe to upgrade automatically.

3 · Why does the drafted changelog never contain a Fixed or a Security section?

Keep a Changelog has six types: Added, Changed, Deprecated, Removed, Fixed and Security. The diff can draft the first four from the contract. The last two are about behaviour and intent, which the contract does not record.
