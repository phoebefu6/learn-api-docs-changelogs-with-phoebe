Where we start

The upgrade reader from session 1 has been waiting five sessions for this page. They do not want to know that v2 is better. Part 1 · covers SemVer and the three API versioning styles

Three numbers, and three places to carry them

6 min live

Semantic Versioning gives a version number a meaning a machine can act on: a dependency range like "any 1.x" is a promise that nothing in 1.x will break you. HTTP APIs then have a second, separate decision that SemVer says nothing about: where in the request the version travels. Three real styles answer it three different ways, and the figure shows what each one asks a client to change when it upgrades.

LiveSemVer for an HTTP API: what the three numbers promise3 min▶

Semantic Versioning 2.0.0 reads MAJOR.MINOR.PATCH. MAJOR goes up for incompatible API changes, MINOR for backward-compatible new functionality, PATCH for backward-compatible bug fixes. Its first rule is the one people skip: the software must declare a public API. For an HTTP API that declaration is the OpenAPI document from session 2. Without it, nobody can say whether a change is compatible, because there is nothing to be compatible with.

Rule 7 is the one this session leans on. MINOR must be incremented when any public API functionality is marked as deprecated. Deprecating is a change in what you promise about the future, so it gets a version of its own. The SemVer FAQ spells out the order: deprecate in a minor release, remove in a later major release, and let at least one minor release carry the deprecation before the removal so users see it coming.

For the Constructed Parcelpoint example that order is exactly 1.5.0 then 2.0.0. Session 5's bench already computed both: v1 to v1.5 is 7 changes, none breaking, MINOR to 1.5.0, and that minor includes the deprecation of GET /lockers/{locker_id}/status; v1 to v2 is 30 changes with 12 breaking, MAJOR to 2.0.0, and the status endpoint is gone. The version numbers are not decoration on the changelog; they are the changelog's headline.

LiveThree places a version can live3 min▶

In the URL path (Google AIP-185). The major version is part of the path: v1, never v1.0. Minor and patch changes are applied in place, so a v1 client simply starts seeing new optional fields. AIP-185 also describes release channels (alpha, beta, stable) and recommends 180 days of notice when deprecating a beta. The version is visible in every log line, link and curl command, and an upgrade means editing every URL.

A date-named version in a header (GitHub REST). At the time of writing (November 2026), GitHub's REST API has two versions, 2022-11-28 and 2026-03-10, chosen with the X-GitHub-Api-Version header. A request with no header gets 2022-11-28. The URL never changes; the version lives in client code, which is tidy until someone forgets to send the header and is silently on the oldest one.

Dated releases pinned per account (Stripe). Each account has a default API version. A Stripe-Version header overrides it for one request, which is how a team tests an upgrade before moving the default. Since 2024-09-30.acacia, Stripe ships monthly releases with no breaking changes and two major releases a year; at the time of writing (November 2026) the current version was 2026-10-28.endive. Re-verify that before you quote it, because it changes every month.

Which one is right? None of them everywhere, and the published practice genuinely disagrees. The path style is the most visible and the bluntest. The header style keeps URLs stable and puts the burden on every client to send it. The account pin protects integrations nobody is maintaining, at the cost of the provider running many versions at once. Pick by asking who pays for an upgrade and who notices a forgotten one, then write your choice into the reference page's first screen.

Self-studyMajor version zero, and why Parcelpoint is past it2 min▶

SemVer rule 4 says that a 0.y.z version is initial development: anything may change at any time, and the public API should not be considered stable. That is an honest label for an API still finding its shape, and a dishonest one for an API with paying users who have been told to build on it.

Parcelpoint (constructed) is at 1.4.2. It declared a public API at 1.0.0, so every 1.x user is owed rule 7 and the FAQ's ordering: a deprecation in a minor, a removal only in a major. The session 5 bench does not model rule 4 at all; it treats every version as post-1.0. If your own API is still 0.x, the bump the bench computes is the one you would owe after 1.0, which is a useful rehearsal and not a requirement yet.

Real world

v1, never v1.0. Google's AIP-185 puts only the major version in the path, and says so plainly: the path carries v1, not v1.0. Minor and patch changes land in place under the same path. The rule is small, and it removes a whole class of client bug: nobody hard-codes a minor version that later disappears.

Part 2 · covers Keep a Changelog and the deprecation signal

Say it in the changelog, then say it on the wire

5 min live

A deprecation has two audiences. The people who read changelogs find it under a ### Deprecated heading. Everyone else, which is most of your callers, only ever sees HTTP responses, so the deprecation has to travel in the response too. Two RFCs give it a standard shape: one header says when the thing was or will be deprecated, the other says when it stops answering. Below is the constructed plan for Parcelpoint's status endpoint.

LiveKeep a Changelog, the parts that matter for a deprecation2 min▶

Keep a Changelog 1.1.0 starts from one idea: changelogs are for humans, not machines. One entry per version, latest first, each with its release date in ISO 8601 (YYYY-MM-DD), and an Unreleased section at the top for what is coming. Changes sort into six types: Added, Changed, Deprecated, Removed, Fixed and Security. A release pulled after shipping keeps its entry, tagged [YANKED], because someone may already have installed it. And it calls dumping a commit log into the changelog "a bad idea", for the obvious reason: commits are written for the people who made the change, not for the people affected by it.

The general craft of changelogs, including tone and how much to say, belongs to Learn Tech Writing, session 6. What is API-specific is the Deprecated type. It is the only one that is a promise about the future, so it must carry two things a normal line does not: what to use instead, and the date after which the old thing goes away.

LiveDeprecation and Sunset, header by header3 min▶

Deprecation, RFC 9745 (March 2025, Standards Track). Its value is a Structured Field Date: an @ followed by Unix seconds. Deprecation: @1796083200 means 2026-12-01 00:00:00 UTC. The date may be in the past (it is deprecated already) or in the future (it will be). A Link header with rel="deprecation" points to human-readable documentation, which for the Constructed Parcelpoint example is the migration guide.

Sunset, RFC 8594 (May 2019, Informational). Its value is an HTTP-date, the same format as Date and Expires: Sunset: Tue, 01 Jun 2027 00:00:00 GMT. After that moment the client should expect the resource to stop answering: a 4xx, a 3xx, or no response at all. The RFC presents it as a hint, not a guarantee, and a rel="sunset" link can point to the policy behind the date.

The rule that ties them. RFC 9745 says the Sunset timestamp MUST NOT be earlier than the Deprecation date. That is common sense written down: you cannot switch something off before you have told anyone it is going. What happens after sunset is your choice within that range; Parcelpoint's constructed plan returns 410 Gone with a body that names the replacement, which is one reasonable reading of "expect a 4xx".

Real world

How long is long enough? GitHub supports a previous REST API version for at least 24 months after a newer one is released; at the time of writing (November 2026), 2022-11-28 is supported until March 10, 2028. Stripe ships two major releases a year and keeps monthly releases free of breaking changes. Google's AIP-185 recommends 180 days for deprecating a beta. Three providers, three windows, and none of them is a standard; Parcelpoint's 182 days is a constructed choice, and yours should be written down before the first deprecation, not argued about during it.

Part 3 · covers the migration guide

One step per broken promise

4 min live

The session 5 bench drafted the constructed Parcelpoint's v2.0.0 changelog from the diff: 30 changes, 12 of them breaking, which merge into ten breaking lines because identical lines across operations collapse into one. Every one of those ten lines is a promise v1 made and v2 breaks. A migration guide is the same ten lines, each turned into an instruction: what to send or read instead, and by when. The machine found the breaks. Only a person can write the "instead".

LiveFrom a changelog line to a migration step4 min▶

Each step has the same four parts: what changed (the drafted line, unchanged), who it hits (which operation, which field), what to do instead (the exact field, parameter or header to send or read), and by when (the sunset date, or "now" if the replacement already exists). Write them in the order a client would hit them during one request, not in changelog order: pagination before parsing, auth before the call.

The "instead" must come from the v2 spec, never from memory. free_slots is a property of Locker in v2; limit is described as lockers per page, up to 100; next_cursor is a string or null, so the loop ends on null. Where the spec is silent, the guide says so. The v2 spec says reservations are "confirmed by webhook" but its webhook event list still only names parcel.delivered, parcel.picked_up and parcel.expired. The honest step says which event to listen for once the constructed Parcelpoint documents it, and flags the gap, exactly like the "none documented" habit from session 3.

Two of the ten steps can start before v2 exists. Parcelpoint 1.5.0 already adds free_slots to Locker and an optional recipient_email to ParcelCreate, which is the whole point of shipping the minor first: users can migrate on their own schedule while v1 still answers. The bench's consumer view says 4 of 6 constructed consumers are hit by v2; a guide that lets them start in 1.5.0 turns a cliff into a slope.

Self-studyWhat the Unreleased section is for during a deprecation2 min▶

Keep a Changelog puts an Unreleased section at the top so people can see what is coming before it ships. During a deprecation window that section does real work: the v2 removals sit there under ### Removed, marked breaking, for the whole six months, so a reader on 1.5.0 can see the exact list they are migrating towards without reading a spec diff.

When 2.0.0 ships, the Unreleased lines move under a ## [2.0.0] - YYYY-MM-DD heading and nothing about their wording changes. That is the test of a good Unreleased line: it is already written for the person affected. If you find yourself rewriting it on release day, it was written for the person who made the change. Diffing tools, release-note generators and changelog linters exist as a category and can keep the section current; none of them can write the "instead".

Real world

GitHub's breaking list is a migration-guide checklist. GitHub's "API Versions" page lists what it treats as breaking: removing an endpoint, removing or renaming a parameter or response field, adding a required parameter, changing a type, removing enum values, adding new validation, and changing authentication. Hold the constructed Parcelpoint's ten lines up against it and every one fits a row. Each row on that list is a sentence a migration guide must contain whenever it happens.

Homework

Before you ship your next breaking change

30 min
  1. Find where your API's version travels. Path, header, account pin or nowhere. Write one sentence saying what a client changes to upgrade, and put it on your reference page's first screen.
  2. Find one thing you would deprecate. Write its Deprecation and Sunset headers with real dates, check that the Sunset date is not earlier, and write the ### Deprecated line with its "instead".
  3. Turn your last breaking release into a migration guide. One step per broken promise: what changed, what to send or read instead, by when. Count how many steps your original release notes were missing.
  4. Score your own docs kit on the six rows above. Write down the weakest row and the reader it fails. That row is your next docs change, and it is usually not the one you expected.
Check yourself

Three questions

Clear all three and session 6 gets stamped in your passport.

1 · The constructed Parcelpoint 1.4.2 marks GET /lockers/{locker_id}/status as deprecated and changes nothing else. Under SemVer 2.0.0, what version should that release be?

A deprecation changes what you promise about the future, so it gets a minor. The removal comes later in a major, and the SemVer FAQ asks for at least one minor carrying the deprecation before it.

2 · A response carries Deprecation: @1796083200 (2026-12-01) and Sunset: Tue, 01 Jun 2027 00:00:00 GMT. Which statement is right?

The Deprecation date may be past or future. RFC 8594 presents Sunset as a hint, not a guarantee, and RFC 9745 only forbids a Sunset earlier than the Deprecation date.

3 · In GitHub's REST versioning, where does the version travel, and what happens if a client sends nothing?

At the time of writing (November 2026) the versions are 2022-11-28 and 2026-03-10. The URL never changes, which is why a forgotten header quietly means the oldest version. The account pin is Stripe's style, the path is Google AIP-185's.
