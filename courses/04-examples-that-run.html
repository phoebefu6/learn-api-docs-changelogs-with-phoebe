Examples that run, and the tests that keep them true

The example in a quickstart is the most copied text in any docs set, and the least checked. It is written once, by hand, on the day the feature ships, and from then on it is a claim about the API that nobody re-reads. Tonight we watch an example drift, check one against the OpenAPI schema mechanically, separate the two gaps a docs set can fall into, and build an example test that fails the moment the API changes underneath it.

Part 1 · covers how examples drift

How a correct example goes wrong without anyone touching it

5 min live

Nobody writes a broken example. They write a correct one, and then the API moves and the example does not. Below is one way the session 1 example could have got that way, reconstructed for the Constructed Parcelpoint example: every step reasonable, every release reviewed, and still a reader on the far end gets a 400.

LiveAn example is a claim; test it like one3 min▶

Read an example the way a reader does: "send exactly this and you will get a 201". That is a claim about the API, as specific as any assertion in a unit test, and it has the same failure mode as untested code. It was true when written. Nothing checks it when the code around it changes. It goes on being shown to people long after it stopped being true.

The fix is not "review the docs more carefully". Reviewers read the diff in front of them, and the release that renamed locker to locker_id touched the spec, not the quickstart page; nothing in that diff pointed at the example. The fix is to give every example the same treatment as code: store it as data, say which operation it belongs to, and run a check that compares it with the spec every time either one changes.

The session 1 example would have failed that check three times over: two required fields missing and one size that is not in the enum. A machine would have caught it at the release that broke it, in seconds. A reader caught it at 4:50 into their first call, in the constructed audit, and some readers never reported it at all.

Self-studyGenerated examples vs hand-written ones3 min▶

One way to stop drift is to stop writing examples by hand: let the docs tooling render a sample request from the schema itself, or from example values stored inside the schema. A generated example cannot use a field name the schema does not have, because it is made from the schema. That is a real guarantee, and teams that generate their reference examples mostly do not see the session 1 kind of drift on those pages.

The cost is that a generated example knows types, not stories. Rendered from the bare schema, POST /parcels becomes a body of placeholder strings; it is valid, and it tells the first-call reader nothing about what a locker id looks like or which size to pick. Hand-written examples carry that meaning, and quickstarts, tutorials and how-to guides are almost always hand-written for that reason.

Practitioners split on where the line goes, and there is no settled answer to quote. The position that holds up either way: whichever way an example is made, it ends up as a payload that can be checked against the schema. Generate where meaning does not matter, write by hand where it does, and test both the same way.

Real world

Docs generated from the code, and the page that still is not. FastAPI generates the OpenAPI description and interactive docs (Swagger UI and ReDoc) from the application code. The interactive page is made from the same description the framework produces from the code, so its request form names the fields that description names. A quickstart written as a separate page in a separate repository has no such link; it is exactly as true as the last person who re-read it. Generation protects the pages it generates and nothing else.

Part 2 · covers validating examples against the spec

Checking an example against the schema it claims to follow

5 min live

The good news from session 2: an OpenAPI 3.1 schema is already a machine-checkable rule. The Schema Object is a superset of JSON Schema Draft 2020-12, so the ParcelCreate schema in the spec can be handed to a JSON Schema validator as it stands, and an example payload can be checked against it with no human judgement involved.

LiveThree checks that need no judgement3 min▶

Required. ParcelCreate lists locker_id, recipient_phone and size as required in v1.4.2. Is each one present in the example? A missing required field is the commonest drift, because renaming a field looks, to a validator, exactly like removing one and adding another.

Type. Every ParcelCreate property is a string. An example that sends a number or null where a string is declared fails here.

Enum. size must be one of small, medium, large, xl in v1.4.2. "M" is a string, so it passes the type check, and it still fails here.

One thing a validator must not do is fail an example for carrying a field the schema does not mention. JSON Schema allows extra properties unless the schema sets additionalProperties: false, and ParcelCreate does not. So locker and phone are reported as "not in the schema" warnings: worth a human look, because they are almost always a typo or an old name, but not a contract violation. A test that fails on what the contract allows teaches people to ignore the test.

Self-studyWhere the examples live, and the tool shelf by category3 min▶

Where examples live. OpenAPI lets you keep example values inside the spec, next to the schema they illustrate. The OpenAPI Initiative's post "Migrating from OpenAPI 3.0 to 3.1.0" (16 February 2021) notes that 3.1 schemas use an examples array in place of the single example keyword of 3.0, because 3.1 schemas are a JSON Schema dialect. Examples stored in the spec are the easiest to test, since the validator finds them without a separate index. Examples in quickstart pages need one extra step: pull each code block out of the page, with a note of which operation it calls.

The tool shelf, as categories. You will not need any of these tonight, and the choice between products is yours. JSON Schema validators are libraries in most languages that check a payload against a schema; they are the engine of an example test. Doc linters check the spec and the docs for rule violations, and many can be set to check example values against their schemas. Mock servers answer requests from the spec alone, so an example can be sent to a mock and checked without the real API. Contract testers send requests to a running server and check its answers against the spec; that is the test in Part 3 that watches the other gap.

Real world

A sample whose examples live inside its schemas. The Swagger Petstore sample (OpenAPI 3.0.4, not 3.1) stores example values next to the fields they illustrate: in its Pet schema, id carries the example 10 and name carries the example doggie. Because they sit beside their type, a validator can check each one against that type with no extra wiring. In a 3.1 document the same values would sit in an examples array; the idea is identical.

Part 3 · covers example tests, contract tests and where they run

Two drifts, two tests

5 min live

A docs set can lie in two places. The docs can disagree with the spec, which is the session 1 example. Or the spec can disagree with the server: the spec says size accepts xl, and the server quietly stopped accepting it. Each gap has its own test, and the most common mistake is to run one and believe you are covered for both.

LiveWhich test catches which lie3 min▶

Four lies a docs set can tell, all from the Constructed Parcelpoint example, and the test that would have caught each one first.

The lieWhere the gap isCaught by
The quickstart sends phone; the spec says recipient_phonedocs vs specExample test
v2 makes recipient_email required; the quickstart never sends itdocs vs specExample test, on the spec change
The spec says POST /reservations answers 201; a server build answers 202spec vs serverContract test
The spec lists xl; a server build rejects itspec vs serverContract test

Where each one runs. The example test needs no server at all: two files in, a list out. Run it on every change that touches docs/ or openapi.yaml, so a spec change that breaks an example fails in the same pull request that made it. The contract test needs a running build, so it runs against a test server whenever the server changes. Wiring either one into a pipeline is a CI job like any other; Learn GitHub for Builders, session 5 covers writing that kind of workflow, and it is not retaught here.

Self-studyWhat a passing example test does not prove3 min▶

A green example test proves one thing: this payload fits this schema. It does not prove that the server accepts it; that is the contract test's job. It does not prove the call succeeds: a valid body still earns a 401 without the X-Api-Key header, or a 409 when the locker has no free slot of that size. It does not check the prose around the example, the base URL in the curl line, or the headers. And it checks format: email only as far as your validator goes; the widget below checks only that recipient_email is a string.

It also proves nothing if it runs against the wrong spec. An example test pinned to last quarter's copy of openapi.yaml passes forever. Point it at the file the release is built from, the same one the session 5 bench diffs, and let it fail when that file moves. Keeping examples, docs and spec in one reviewed pipeline is docs-as-code territory, and Learn Tech Writing, session 7 owns it.

Real world

A breaking-change list, read with two tests in mind. GitHub's REST "API versions" page lists what it treats as breaking: removing an endpoint, removing or renaming a parameter or response field, adding a required parameter, changing a type, removing enum values, adding new validation, and changing authentication. Almost every item on that list is visible in the spec, so an example test run on every spec change flags the examples each one breaks. "Adding new validation" is the item most likely to live only in server code, where only a contract test, or a customer, will notice it.

Fix the example for v2. Add recipient_email to the body (type it into the box, or paste the one below) and test against v2.0.0. Then test the same body against v1.4.2: it still passes there, with one warning, because v1.4.2's ParcelCreate does not name recipient_email and does not forbid extra fields. That is exactly the body a migration guide wants: one example that works on both sides of the upgrade.

Plant a fault before you trust it. A test you have only ever seen pass might not be able to fail. Before wiring the CI step, change one example to "size": "xl" and run it against v2.0.0: it must print value not in enum: size "xl" is not one of small, medium, large. If it passes, the test is decoration.

Homework

Before session 5

30 min
  1. Count your examples. List every request example in your own API's docs: quickstart, guides, reference. Mark each one generated or hand-written, and note whether anything checks it today.
  2. Test three by hand. Pick three hand-written examples and check each against its schema in the spec: required fields, types, enum values. Write the failures in the widget's format, one line each.
  3. Name your two tests. For your API, write down what plays the example test and what plays the contract test today. If the answer to either is "a customer", that is the first one to build.
  4. Draft the CI step for your repo. Adapt the step 4 sketch to where your spec and docs actually live, and hand it to whoever owns your pipeline.
Check yourself

Three questions

Clear all three and session 4 gets stamped in your passport.

1 · The quickstart example was correct when it was written and nobody has edited it since. Why does it still need a test?

The session 1 example drifted with no one touching it. The spec moved and the example stayed. Treat the example like code: store it as data and check it against the spec whenever either changes.

2 · The quickstart sends phone but the spec says recipient_phone. Which test catches that, and where does it run?

That is drift between the docs and the spec, so the example test owns it. The contract test watches the other gap, the spec against the running server, and would pass happily here.

3 · The fixed example passes against v1.4.2. What happens when the same body is tested against v2.0.0?

In v2.0.0, recipient_phone becomes optional, not removed, and only xl leaves the size enum. The one new failure is the new required field, which is exactly the line the widget prints in step 3.
