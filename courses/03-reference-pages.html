Reference pages that answer the real question

Nobody reads a reference page for pleasure. They arrive with a status code in one hand and a production incident in the other, and they want the answer before the next alert fires. Tonight we take the OpenAPI document from session 2 and turn one operation of it into a reference entry that serves that reader: the seven things every entry owes, errors written as code, cause and fix, and the three questions most pages dodge, rate limits, pagination and whether a retry is safe. The operation is POST /parcels from the Constructed Parcelpoint example.

Part 1 · covers what an endpoint page owes the reader

Seven things, in the order of the spec

6 min live

The debug reader from session 1 does not read a reference entry top to bottom. They jump to the part that matches the symptom, read three lines and leave. That only works if every entry has the same parts in the same place, so the reader learns the shape once and can find the 409 on any page of your API without thinking. Here is the shape, drawn on the entry we rewrite tonight.

LiveThe seven things every endpoint entry owes4 min▶

1 · What it does, in one line. A verb and an object, from the reader's side: "Registers a parcel for delivery to a locker." Not the history of the feature, not a sales line.

2 · Auth. Which credential, and where it goes. Parcelpoint v1 declares one API-wide scheme, an API key sent as the X-Api-Key header, so every entry says so, even though it is "the same everywhere". The debug reader landed on this page from a search result and never saw your auth guide.

3 · Path and query parameters. Name, type, required or not, and what it means. When there are none, as on POST /parcels, say "none" rather than leaving the heading out; an absent heading reads as "forgot", a "none" reads as "checked".

4 · Body fields. One row per field: name, type, required, allowed values, one line of meaning. For Parcelpoint that is locker_id, recipient_phone and size, all required, size one of small, medium, large or xl.

5 · Every response code, with its meaning. The success code and every error the call can actually return, each with what it means, the likely cause and the fix. Part 2 is about this block.

6 and 7 · A real request and the real response. A call that would work if pasted with a real key, and the body it returns, so the reader can compare shape against shape. Constructed values are fine; pretend outputs are not, so say the values will differ.

Why in this order. The Diataxis framework's advice for reference is to describe the machinery and mirror the structure of the product; for an API, the structure of the product is the spec, so the entry follows the spec's own order: operation, security, parameters, request body, responses. The four doc kinds in full are Learn Tech Writing, session 5, and general reference craft is session 6 there. This card is only what changes when the product is an API.

Self-studyGenerated vs hand-written reference: what generation cannot write4 min▶

Reference renderers that turn an OpenAPI document into pages exist in many flavours, and they are a good idea: blocks 2 to 7 come straight out of the spec, so they cannot drift from it. Generate those. But look at what the Parcelpoint v1.4.2 spec actually holds for the 409: the description "The locker has no free slot of that size." and a pointer to the Error schema. That is the meaning. Three things are missing, and no generator can invent them.

The why. Why would a locker have no free slot when the caller's request was fine? The answer (other traffic into the same locker, slots held by reservations, whatever is true for this API) lives in someone's head on the API team, not in the schema. The page needs that sentence, confirmed by the people who run the service.

The fix. "Try another size or another locker, and check free slots first with GET /lockers/{locker_id}/status." The spec knows that endpoint exists; it does not know it is the cure for this 409.

The gotcha. The Parcel schema marks only parcel_id, status and locker_id as required. pickup_code and created_at are not. A generated table will print that faithfully, and the reader will still write parcel.pickup_code without a null check, because nothing told them when it can be absent. The page should say when, or say the spec does not promise it.

The working pattern: generate the skeleton from the spec, and keep the why, the fix and the gotcha in the spec's own description fields where you can, so they travel with the contract instead of living in a page that drifts. Session 4 adds the test that keeps the examples honest.

Real world

Seven blocks, in the wild. GitHub's REST reference entry for "Create an issue" carries the same skeleton: headers, path parameters, body parameters, a list of HTTP response status codes (201, 400, 403, 404, 410, 422 and 503) and code samples. The list is specific to that call. A 410 there means something about issues on that repository, not a lecture on HTTP. That is the bar: every code listed is one the caller can actually get, from this operation.

Part 2 · covers errors with codes and fixes

Every code gets a cause and a fix

5 min live

A status code tells the caller that something happened. It does not tell them what to do next, and "what to do next" is the only thing the debug reader came for. So each code on the page gets three columns: what it means, the likely cause, and the fix, plus the shape of the error body the caller will be parsing. Here is POST /parcels worked through, including one code the v1 operation never lists.

LiveCode, cause, fix: three columns3 min▶

Meaning is what the server decided. The spec already has it: "The locker has no free slot of that size." Cause is what the caller probably did, or what happened in the world, to get there: their request was fine, and the locker filled up. Fix is the next action, written as an instruction: try another size or locker, and check free slots first.

The cause column is what separates 400 from 409 for a tired reader. Both are "it did not work". One means "your request is wrong, change it"; the other means "your request is right, the world said no". A caller who cannot tell them apart will either retry a 400 forever or rewrite a body that was never broken.

Then the body. Every Parcelpoint error, whatever the code, comes back as the Error schema: an object with a code string and a message string, both required. The page shows that shape once per entry, because the caller's error handler parses it. One honest gap shows up straight away: v1 says code is a string but never lists which strings. A caller who wants to branch on "no free slot" versus "unknown locker" has nothing to branch on. The reference page should list the values, or say plainly that they are not yet documented and the caller should branch on the status code.

How the message itself should be worded, so a human can act on it, is its own craft, and it lives in Learn Tech Writing, error messages. Here we only make sure the page has a place for each code and says what to do.

Self-studyDocument the errors you return, not the ones HTTP defines3 min▶

A tempting shortcut is a shared table of every HTTP status code, linked from every entry. It answers nothing. The reader with a 409 on POST /parcels does not need to learn that 409 means Conflict in general; they need to know what conflicted, here. List the codes this operation returns, and only those.

"Only those" cuts both ways. The v1.4.2 operation lists 201, 400 and 409. But the whole API sits behind security: apiKey, so a missing key on POST /parcels will get a refusal, and the operation never says which code. In the spec, GET /lockers lists a 401 with "Missing or invalid API key."; POST /parcels does not. The reference page should show 401 for this call, and the better fix is upstream: add the 401 response to the operation in the spec, so the generated page, the example test in session 4 and the bench in session 5 all see it.

The same audit question works on any endpoint you own: for each code your server can send from this operation, is it on the page? For each code on the page, can the server actually send it? A mismatch in either direction is a defect.

Real world

Machines read your error list too. oasdiff, an open-source tool that compares two OpenAPI documents, treats response codes differently by kind: removing a success status from an operation is reported as breaking, while removing or adding a non-success status is reported as info. That only works if the codes are written down per operation. An error the spec never lists is an error no diff will ever warn anyone about. Session 5 runs a checker built on the same idea.

Part 3 · covers rate limits, pagination and idempotency

Say it even when the answer is "none"

4 min live

Three questions come up on every integration, usually at the worst moment: how fast may I call this, how do I get the next page, and if my request timed out, is it safe to send it again? A reference page that is silent on any of them is not neutral. The reader fills the silence with a guess, and the guess becomes production code. Parcelpoint v1 documents no rate limit and no way to make a retry safe; the page has to say so, and this is what is at stake on the retry.

LivePagination on the page that paginates2 min▶

POST /parcels returns one object, so its entry has no pagination section, and should not grow one. Pagination belongs on the entry of the operation that pages, in the parameters and response blocks, where the reader is looking when they need it. A separate "Pagination" guide is a fine how-to; it is not a substitute.

v1, page numbers. GET /lockers takes page (starting at 1) and per_page (up to 100), and every response carries page and total_pages beside data. The entry should say what the default page size is, or that the spec does not set one, and that you stop when page equals total_pages.

v2, cursors. In the v2 document the same operation takes cursor and limit (up to 100) and returns next_cursor, a string or null. The entry has to say the two things a cursor reader always gets wrong: the cursor is opaque, so pass it back exactly as received, and a null next_cursor means the last page. There is no total_pages any more, which is exactly why the Partner analytics export, a constructed consumer, breaks in session 5.

Self-studyIdempotency: say whether a retry is safe4 min▶

An operation is idempotent when sending it twice has the same effect as sending it once. Reads are, by nature. DELETE /reservations/{reservation_id} is close: the second call finds nothing to delete (in the v2 document its description says plainly that cancelling twice returns 404). POST /parcels is not: each call registers a parcel.

The trouble is the timeout. When the client gives up waiting, it cannot know whether the server never got the request, or got it, registered parcel A and lost the reply. Retrying is correct in the first case and creates a duplicate in the second. Some APIs let the client attach a value the server remembers, so a repeat of the same value returns the first result instead of acting again; the figure calls it a "retry key", a constructed label, because the name and the mechanism vary from API to API.

Parcelpoint v1 documents no such mechanism. So the honest page says three things: retrying POST /parcels after a timeout may register a second parcel; before retrying, check whether the first one exists; and v1 offers no listing of your parcels to check with (a GET /parcels list only arrives in v1.5 and v2). That last sentence is uncomfortable, and it is the most useful line on the page. It also belongs in a ticket for the API team.

Rate limits, the same way. v1.4.2 documents no rate limit and no rate-limit response. Do not invent a number to fill the slot. Write "No rate limit is documented for v1" and raise it, because a documented "none" is a promise the team can be held to, and an undocumented one is a guess every caller makes differently.

Real world

Depth on request. Stripe's API reference collapses nested parameters by default and expands them when the reader asks. The top level of an entry stays short enough to scan for the one field you came for, and the full depth is one click away. It is the same principle as the seven blocks: a fixed, scannable shape first, detail where the reader chooses to go.

Check yourself

Three questions

Clear all three and session 3 gets stamped in your passport.

1 · A partner's checkout gets a 409 from POST /parcels. Where should they find the answer, and what should it say?

The debug reader needs what conflicted here and what to do next, on the page for the call they made. A generic HTTP table explains the word Conflict and nothing else; the quickstart is for a different reader.

2 · The v1 spec already gives each POST /parcels response a one-line description. Why does the reference page still need a cause and a fix for each code?

Meaning, cause and fix answer three different questions. Without the cause column a caller retries a 400 forever or rewrites a body that was never broken. Generated pages are fine for the skeleton; the cause and fix are what a human adds, ideally in the spec's own description fields.

3 · A POST /parcels call times out. Parcelpoint v1 documents no way to mark a request as a repeat. What should the reference page tell the caller?

A timeout does not tell the client whether the server acted. POST is not idempotent by nature, and v1 offers no mechanism to make it so, so the honest page says a retry is unsafe. Inventing a rate limit or interval the API never documented would be a new promise nobody made.
