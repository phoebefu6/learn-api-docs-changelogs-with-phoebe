Part 1 · covers the document's shape: root, paths, operations, parameters

A document a reader walks from the top

6 min live

An OpenAPI document looks long, but it is a tree with a small number of branches, and it reads in the same order every time: the root says what this API is and where it lives, paths lists the URLs, each path holds operations keyed by HTTP method, and each operation says what goes in and what comes out. Learn the order once and every OpenAPI file you open afterwards, yours or a vendor's, reads the same way.

LiveRoot, paths, operations, in the order a reader meets them4 min▶

The root. The OpenAPI Specification 3.1 lists ten root fields: openapi, info, jsonSchemaDialect, servers, paths, webhooks, components, security, tags and externalDocs. Only two are required, openapi (the spec version, here 3.1.0) and info (title and the API's own version, here 1.4.2), and the document must also contain at least one of paths, components or webhooks. Note the two versions: openapi is the version of the format, info.version is the version of your API. Session 5 bumps the second one, never the first.

Paths. Each key is a URL template relative to the server, such as /parcels or /lockers/{locker_id}. Under each path sit the operations, keyed by lowercase method: get, post, delete and so on. Parcelpoint v1 has eight paths and one operation on each.

Operations. An operation is the thing a reference page is about. Its fields include operationId, parameters, requestBody, responses, callbacks, deprecated (false unless you say otherwise), security and servers. Responses are keyed by status code, and each one says what body comes back.

Parameters. Every parameter states where it lives with in, which takes exactly four values: path, query, header or cookie. locker_id in /lockers/{locker_id} is a path parameter and must be marked required; page, per_page and city on GET /lockers are query parameters. A JSON body is not a parameter at all: it is the requestBody.

Self-studyservers, security schemes, tags, operationId: the fields people forget3 min▶

servers. The base URL, with its version, is the first thing a first-call reader needs, and session 1's example lost /v1 because it lived nowhere official. Put it in servers and every generated example inherits it.

security and securitySchemes. Two halves that people often write only one of. components.securitySchemes defines how a credential is sent (Parcelpoint: an apiKey in the X-Api-Key header); the root security says which scheme applies by default, and an operation can override it. A spec with a scheme defined but no security requirement documents an API that needs no key, which is a lie the reference page will repeat.

tags. Tags group operations, and most reference generators turn each tag into a section of the navigation. Without them the reference is sorted however the tool likes. Parcelpoint v1 has none yet; session 3 decides what the reader's sections should be.

operationId. A unique, stable name per operation, such as listLockers or createParcel. Generated client libraries name their methods after it and docs tools build anchors from it, so renaming one is a change your users feel even though no URL moved. Choose it once, as a verb plus a noun, and leave it alone.

Real world

The best-known sample spec, written spec first. The Swagger Petstore is the sample API most OpenAPI tools demo against. Its README says the project's third iteration "switched to the design first approach": the OpenAPI document is written and maintained as the source, and the sample server follows it. One caution before you copy from it: the current Petstore sample is OpenAPI 3.0.4, not 3.1, so it still uses the 3.0 shapes Part 2 warns about.

Part 2 · covers components, $ref and JSON Schema in 3.1

Write a schema once, point at it everywhere

5 min live

components is where a document keeps the things more than one operation needs. Each reuse is a $ref, a pointer like #/components/schemas/Locker, not a copy. That one design choice is why an OpenAPI file can be the docs kit's single source: change the schema in one place and every operation, every generated page and every diff sees the change at once. Since 3.1, the schemas themselves are JSON Schema, which retired a few habits that older specs are full of.

LiveWhy $ref is the docs kit's single source3 min▶

components can hold ten kinds of reusable thing: schemas, responses, parameters, examples, requestBodies, headers, securitySchemes, links, callbacks and pathItems. Most specs live on the first two plus securitySchemes. Anything an operation needs can be written inline instead, and for a shape used exactly once that is fine. The moment a shape appears twice, give it a name in components and point at it.

The pay-off is not shorter YAML. It is that a change has one address. In the Constructed Parcelpoint example, Locker is defined once and both locker operations point at it; if v2 renames locker_id to id there, both operations, both reference pages and the diff all see the rename, and nobody has to remember the second copy because there is no second copy.

The same property makes changes look big, honestly. In session 5's bench, the edited Swagger Petstore preset changes one schema, Pet.status, and that one edit produces seven change rows: two operations that no longer accept the value, and five that no longer return it. That is not noise. Every one of those operations really did change for its caller, and a changelog that listed only "edited Pet" would hide which calls to retest.

Self-studyFour 3.0-to-3.1 changes you will meet in an old spec3 min▶

In 3.1, the Schema Object is "a superset of the JSON Schema Specification Draft 2020-12". In 3.0 it was a cousin of JSON Schema with its own rules. The OpenAPI Initiative's migration post (16 February 2021) lists what that means in practice. These four are the ones a 3.0 spec is most likely to contain:

  1. nullable is gone. type: string with nullable: true becomes type: [string, "null"]. The quotes around null matter: unquoted, YAML reads it as an empty value, not the string "null".
  2. exclusiveMinimum and exclusiveMaximum are numbers. 3.0 wrote minimum: 0 plus exclusiveMinimum: true; 3.1 writes exclusiveMinimum: 0 on its own.
  3. A schema's example becomes examples, an array. This is the schema keyword only; example fields on parameters and media types are a separate thing and are not part of this change.
  4. The document declares itself as 3.1. openapi: 3.1.0 (or 3.1.1) tells tools to read schemas as JSON Schema 2020-12, which is what makes the other three valid. A file that says 3.0 but uses type arrays is broken in both versions.

Not every tool reads 3.1 yet, which is why plenty of real specs, the Petstore sample among them at 3.0.4, still use the 3.0 shapes. When you inherit one, convert it in a single reviewed change, not field by field as you touch it.

Real world

The migration post as a checklist. When OpenAPI 3.1.0 was published on 15 February 2021, the OpenAPI Initiative followed it the next day with "Migrating from OpenAPI 3.0 to 3.1.0", a short list of the edits to make by hand. It is the most useful single page to have open when you upgrade a spec: the version line, nullable to type arrays, exclusive bounds as numbers, examples as arrays. The current 3.1 patch release, 3.1.1, is dated 24 October 2024 and keeps the same shapes. A newer minor version, OpenAPI 3.2.0, was published on 19 September 2025 and adds features such as a query method and a querystring parameter location. Everything on these pages is 3.1, which is what Parcelpoint's documents and the session 5 bench use; check which version your own tools read before you upgrade.

Part 3 · covers spec-first versus code-first, a contested choice

Who writes the contract first

4 min live

Teams argue about this with real conviction, and both sides ship good APIs. Spec-first teams write the OpenAPI document before the code and review it like code. Code-first teams write the handlers and let the framework generate the document. There is no published evidence that settles which produces better docs, so this Part gives no verdict. It shows where each workflow authors the contract, where drift can slip in, who gets to review the contract, and what each costs.

LiveTwo honest workflows3 min▶

Spec-first. Someone writes the OpenAPI document and opens a pull request with no code in it. API reviewers, the docs writer and, ideally, a consumer team read the contract while it is still cheap to change. Once merged, the reference, mock servers and test stubs are generated from it, and the server is built to match. What it costs: the contract is written twice in effect, once as YAML and once as code, and keeping them equal needs a test that fails when they differ (session 4). Where it drifts: at the server, which can quietly accept or return something the document never mentioned.

Code-first. Engineers write handlers with typed request and response models, and the framework produces the OpenAPI document from them, usually serving interactive docs from the same running code. There is one thing to keep up to date, and the document cannot disagree with the types. What it costs: the contract is shaped by whatever the framework emits, descriptions and examples live in code annotations that engineers write, and nobody reviews "the contract" as such. Where it drifts: at the handlers, where renaming a model field in a refactor renames a public field, and the pull request reads like an internal tidy-up.

Who reviews the contract is the real difference. Spec-first puts the contract in front of reviewers on purpose. Code-first can do the same, but only if the team adds that step, which is the self-study card below.

Self-studyHybrid: generate from code, diff in review2 min▶

Many code-first teams close the review gap without changing how they write code: the build generates the OpenAPI document, commits it (or attaches it to the pull request), and a diff of that document against the last release appears in review. A reviewer who would never spot a renamed field in a model class will spot "locker_id removed" in a contract diff.

That is exactly what session 5's bench does: it compares two OpenAPI documents and does not care whether a person or a framework wrote them. So whichever side your team is on, the deliverable for session 5 is the same, a JSON copy of the document for the release you shipped and the one you are about to. Tooling exists for every part of this (spec editors, mock servers, contract testers, diff checkers in CI); choose by category and by what your team already runs, since none of it is needed to follow these six sessions.

Real world

A framework that writes the spec for you. FastAPI, a Python web framework, lists among its features that it generates an OpenAPI description and interactive API documentation straight from the application code: the types you declare for a request and a response become the schemas in the document. It is the clearest working example of the code-first side, just as the Petstore README is of the spec-first side. Read both feature lists and you have the two cases in their own words.

Build-along

Parcelpoint v1.4.2 in OpenAPI 3.1

★ 22 min · everyone builds

You will write two operations of the Constructed Parcelpoint example in OpenAPI 3.1 YAML: GET /lockers and POST /parcels, plus the shared schemas they point at. Type each step into a file of your own before you look at the box under it; the boxes match, field for field, the v1.4.2 document the session 5 bench loads. Any text editor will do, and nothing needs to run.

Write the root: what this is, where it lives, how to authenticate. Two version lines that mean different things, one server with the version in the URL, and a default security requirement that points at a scheme you will define in step 2.

★ Step 1 · root fields (constructed Parcelpoint v1.4.2)openapi: 3.1.0 info: title: Parcelpoint API (constructed example) version: 1.4.2 description: Lockers, parcels, reservations and pickup webhooks. servers: - url: https://api.parcelpoint.example/v1 security: - apiKey: []

Write the shared pieces in components. The security schemes, and the four schemas these two operations need: Locker, ParcelCreate (what you send), Parcel (what you get back) and Error. Note the size enum, exactly four lowercase values, and which fields each required list names. The full v1 document also has a Reservation schema; it belongs to /reservations, which is not part of tonight.

★ Step 2 · components (bearer is defined in v1 but used by nothing yet)components: securitySchemes: apiKey: type: apiKey in: header name: X-Api-Key bearer: type: http scheme: bearer schemas: Locker: type: object required: [locker_id, address, city] properties: locker_id: {type: string} address: {type: string} city: {type: string} size_classes: type: array items: {type: string, enum: [small, medium, large, xl]} open_24h: {type: boolean} ParcelCreate: type: object required: [locker_id, recipient_phone, size] properties: locker_id: {type: string} recipient_phone: {type: string} size: {type: string, enum: [small, medium, large, xl]} Parcel: type: object required: [parcel_id, status, locker_id] properties: parcel_id: {type: string} status: {type: string, enum: [created, in_locker, picked_up, expired]} locker_id: {type: string} pickup_code: {type: string} created_at: {type: string, format: date-time} Error: type: object required: [code, message] properties: code: {type: string} message: {type: string}

Write GET /lockers. Three optional query parameters, a 200 whose body is a page of lockers pointing at Locker, and a 401 pointing at Error. Quote the status codes: in YAML an unquoted 200 is a number, while JSON object keys are always strings.

★ Step 3 · paths./lockerspaths: /lockers: get: operationId: listLockers summary: List lockers description: Returns lockers, one page at a time. parameters: - name: page in: query required: false description: Page number, starting at 1. schema: {type: integer} - name: per_page in: query required: false description: Lockers per page, up to 100. schema: {type: integer} - name: city in: query required: false description: Only lockers in this city. schema: {type: string} responses: "200": description: A page of lockers. content: application/json: schema: type: object required: [data, page, total_pages] properties: data: type: array items: {$ref: "#/components/schemas/Locker"} page: {type: integer} total_pages: {type: integer} "401": description: Missing or invalid API key. content: application/json: schema: {$ref: "#/components/schemas/Error"}

Write POST /parcels. A required JSON body that points at ParcelCreate rather than restating it, and three responses: 201 with the new Parcel, 400 for an invalid body, 409 when the locker has no free slot of that size. This sits under the same paths: key as step 3.

★ Step 4 · paths./parcels, with the $ref jump /parcels: post: operationId: createParcel summary: Create a parcel description: Registers a parcel for delivery to a locker. requestBody: required: true content: application/json: schema: {$ref: "#/components/schemas/ParcelCreate"} responses: "201": description: Parcel created. content: application/json: schema: {$ref: "#/components/schemas/Parcel"} "400": description: The request body is invalid. content: application/json: schema: {$ref: "#/components/schemas/Error"} "409": description: The locker has no free slot of that size. content: application/json: schema: {$ref: "#/components/schemas/Error"}

Check session 1's broken example against what you wrote. Read the body from the old landing page against ParcelCreate, key by key, the way a validator would. Write your list first. One subtlety: ParcelCreate does not set additionalProperties: false, so by the schema alone the unknown keys are tolerated; the request fails because the required ones are missing.

★ Step 5 · the session 1 body, checked against ParcelCreateBody from session 1: {"locker": "LK-0042", "phone": "+1 555 0100", "size": "M"} locker_id required -> missing ("locker" is not a ParcelCreate field) recipient_phone required -> missing ("phone" is not a ParcelCreate field) size required -> present, but "M" is not in [small, medium, large, xl] Verdict: 400, three mismatches. The fix is the spec's names and "medium". The spec is now the referee: whichever page disagrees with it is the page to fix.

Keep a JSON copy. The session 5 bench reads JSON only; it does not load a YAML parser. Convert your file with any YAML-to-JSON converter you trust, or by hand for a file this size, and keep both. YAML is easier for people to review; JSON is what the diff reads. The start of the JSON copy looks like this.

★ Step 6 · the same tree, as JSON (first lines){ "openapi": "3.1.0", "info": { "title": "Parcelpoint API (constructed example)", "version": "1.4.2", "description": "Lockers, parcels, reservations and pickup webhooks." }, "servers": [{"url": "https://api.parcelpoint.example/v1"}], "security": [{"apiKey": []}], "paths": { "/parcels": { "post": { "operationId": "createParcel", "requestBody": { "required": true, "content": { "application/json": { "schema": {"$ref": "#/components/schemas/ParcelCreate"} } } }, ...

Read it aloud before you trust it. Walk your file the way Part 1 walked the tree: root, then /lockers, then /parcels, then every $ref to the schema it lands on. A $ref with a typo in the schema name is the most common mistake in a hand-written spec, and it is invisible until a tool tries to follow it.

Homework

Before session 3

30 min

  2. Find your own contract. Open your API's OpenAPI file, generated or hand-written. Note its openapi version, whether it has servers, security and operationId on every operation, and how many schemas are inline instead of in components.
  3. Hunt the 3.0 habits. Search the same file for nullable, exclusiveMinimum: true and a schema-level example. Each hit is a line to change if you move to 3.1.
  4. Name your team's workflow. In two sentences: is your contract authored spec-first or code-first, and at which point in your process does a person review it as a contract? If the answer is "nowhere", write down where the session 5 diff could sit.
Check yourself

Three questions

Clear all three and session 2 gets stamped in your passport.

1 · Which root fields does the OpenAPI 3.1 Specification require in every document?

The specification marks exactly two root fields REQUIRED and adds the at-least-one rule. servers and security are optional to the format but close to mandatory for a reader: without them the docs cannot say where to call or how to authenticate.

2 · You inherit a 3.0 schema with type: string and nullable: true. How do you write the same field in OpenAPI 3.1?

The OpenAPI Initiative's migration post lists it first: nullable is gone and a type array with "null" replaces it. A default value says what is assumed when the field is absent, which is a different promise from "this field may be null".

3 · Why does keeping Locker in components and pointing at it with $ref matter when the API changes?

Inline schemas are allowed; they just make every change a hunt for copies. And a $ref shows changes rather than hiding them: in session 5's edited Petstore preset, one edit to Pet.status produced seven change rows, one per operation that really changed for its caller.
