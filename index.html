Learn API Docs & Changelogs with Phoebe

Reference pages, examples that run, and a changelog someone can act on. Write the spec first, keep every example working, and ship a breaking change without breaking trust. A developer meets your docs before they meet your endpoint, so for them the docs are the interface. Six sessions around two questions: could a stranger make a first successful call in five minutes, and when version 2 lands, would they know from your changelog exactly what to do? One running case throughout, Parcelpoint, a constructed parcel-locker API whose docs you rebuild piece by piece, and a real OpenAPI diff engine in the browser that classifies every change and drafts the changelog.

The six sessions 🎯 · from a five-minute audit to a deprecation a reader can act on

The running case is Parcelpoint, a constructed parcel-locker network with a public REST API: lockers, parcels, reservations and pickup webhooks. Its v1 docs grew one page at a time; its v2 renames fields, changes pagination and removes an endpoint. Each session adds one piece to Parcelpoint's docs kit.

👀 Session 1 · foundations

Docs as the API's interface: who reads them and what they need

The five jobs readers bring to API docs, time to first call as the number that matters, and the four doc kinds applied to an API. Build-along: a five-minute audit of the Parcelpoint v1 docs, scored.

▶ Start here 📐 Session 2 · foundations

Spec-first: describing an API in OpenAPI 3.1

Paths, operations, parameters, request bodies, responses, components and $ref, and what JSON Schema alignment changed in 3.1. Spec-first against code-first, argued from both sides. Build-along: /lockers and /parcels in YAML.

the one source 📖 Session 3 · core

Reference pages that answer the real question

What every endpoint page owes the debug reader: auth, errors with codes and fixes, rate limits, pagination, idempotency and a real example per operation. Build-along: rewrite one Parcelpoint endpoint page.

the debug reader 🧪 Session 4 · stretch

Examples that run: quickstarts, samples and tests that keep them true

Examples generated from or validated against the spec, doc tests in CI, and the drift between docs and API. Build-along: a quickstart plus a test that fails the moment an example stops working.

drift fails a build 🔍 Session 5 · bench night

The bench: changelog checker

A real OpenAPI diff in your browser: every change classified breaking, non-breaking or docs-only, the SemVer bump it forces and a drafted changelog entry. Then ship a breaking change as a minor and count who breaks.

★ the bench 🌅 Session 6 · capstone

Versioning and deprecation: a changelog someone can act on

SemVer and the three API versioning styles, Keep a Changelog categories, the Deprecation and Sunset headers, migration guides and timelines. Capstone: Parcelpoint's whole docs kit, scored.

Choose your path 🗺️

Three doors into the same conviction: the docs are the contract developers code against, so they must be generated from or tested against one source, and every change to that source must be classified before it ships.
